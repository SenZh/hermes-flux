## 一、它解决的问题

### 1.1 三个具体痛点

| 痛点 | 现象 | 根因 |
|---|---|---|
| **冷启动白屏** | 打开应用，左轨要等 200~800ms 才出内容 | 会话列表只存在内存 `state` 里，进程一死就没了，重启必须等 `GET /api/sessions` |
| **离线完全不可用** | 网关没起来，点任何会话都是空白 | 消息只在 `sessionMessagesCache`（内存 Map），没有磁盘副本 |
| **在途写入被误删** | 用户刚发的消息，几秒后自己消失 | 拉取响应用"远端最大行号"做删除上界，把拉取期间新写的行当成幽灵 |

三条都指向同一件事：**本地没有可信的、可恢复的副本**。

### 1.2 一句话原理

> **缓存是内存 `state` 的启动快照，不是运行期读路径。**

推导一下为什么只能是这个定位：

```text
如果缓存参与运行期读  ──►  就要回答 TTL / 写穿透 / 冲突仲裁 / 一致性协议
                        ──►  复杂度指数上升
而收益  ──►  省掉一次 50ms 的 REST 请求
```

所以设计成：**启动时读一次，权威结果到达后写一次**。中间所有读都走 `state`。

## 二、分层与职责

### 2.1 四层结构

```text
┌──────────────────────────────────────────────────────────────────────┐
│  Renderer（壳层）                                                     │
│  · restoreCacheToState()   启动时读一次                              │
│  · persist*ToCache()       权威结果到达后写一次                       │
│  · 运行期所有读走 state，不缓存                                    │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ 调用
┌────────────────────────────▼─────────────────────────────────────────┐
│  CacheService（core 编排层，零 DOM / 零宿主 API）                      │
│  · 索引信封读写 + 版本校验 + 上限裁剪                                  │
│  · 通道级串行锁（同通道读改写不交叉，不同通道并行）                     │
│  · applyRemoteWindow / truncate 的完整编排                            │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ 调用
┌────────────────────────────▼─────────────────────────────────────────┐
│  cacheMerge（core 纯函数层，零 IO）                                   │
│  · upsertMessageRows    同主键择优                                    │
│  · mergeRemoteWindow    围栏剔除（核心）                              │
│  · applyTruncation      截断重绑定                                    │
│  · evictToCap           按 orderKey 淘汰                              │
│  · buildChannelBounds   主键区间计算                                  │
└────────────────────────────┬─────────────────────────────────────────┘
                             │ 实现
┌────────────────────────────▼─────────────────────────────────────────┐
│  ICacheStore（存储抽象）                                              │
│  · MemoryCacheStore    测试 / 降级 / 行为基准                         │
│  · DesktopCacheStore   localStorage（索引） + IndexedDB（消息）       │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 为什么纯函数要单独成层

因为**只有纯函数能被形式化验证**。

`mergeRemoteWindow` 的围栏条件由三个布尔项共同决定（`> remoteMax`、`<= fenceMax`、`not pending`）。把它和一个 `await store.listMessages()` 写在一起，就没法用 fast-check 在随机交错下证明它。

分层之后，验证器直接调编译产物 `cacheMerge.mergeRemoteWindow`，反例可以在代码里一行行复现。

### 2.3 两类数据，两种介质

| 数据 | 介质 | 大小 | 必须同步的原因 |
|---|---|---|---|
| 会话 / 群聊 / Agent 索引 | localStorage | < 100 KB | 首屏要立刻可见，异步读会多一帧空白 |
| 头像 | localStorage | < 2 MB | 同上，避免方块渐显 |
| 消息正文 | IndexedDB | 10 万行级 | localStorage 5MB 配额装不下；且配额失败是**连坐**的——同一次写入的索引会一起丢 |

## 三、数据模型与主键

### 3.1 消息行主键：四元组

```text
(profile, channel, channelId, orderKey)
     │         │        │           │
     │         │        │           └─ session: rowId（网关行号）
     │         │        │              room   : seq（房间内序号）
     │         │        └─ 会话 ID 或房间 ID
     │         └─ 'session' | 'room'
     └─ 归属 Profile；群聊固定 ''
```

**为什么必须四元组**：

- 同一个 `sessionId` 可能存在于多个 Profile → 少了 `profile` 会互相覆盖
- 单会话用 `rowId`、群聊用 `seq`，两个序号空间无关 → 少了 `channel` 会主键碰撞
- 不同会话的 `rowId` 从 1 开始 → 少了 `channelId` 全部重叠

### 3.2 为什么排序只看 `orderKey`

| 候选 | 问题 |
|---|---|
| `timestamp` | 秒级时间戳归一化后同秒并列，无法定序 |
| `timestamp`（毫秒） | 客户端 `Date.now()` 与服务端时钟不可比，混排会倒挂 |
| `orderKey` | 网关分配的单调序号，唯一可靠 |

### 3.3 索引信封

```jsonc
{ "v": 1, "savedAt": 1730000000000, "items": [...] }
```

`v` 不匹配 → 整体丢弃重建。**不写迁移代码**：索引条目少，重建成本 = 一次网络请求。

## 四、核心原理：围栏（Fence）

这是整个组件里唯一"写错了会丢用户数据"的地方，值得单独讲。

### 4.1 问题场景

```text
时间 ──────────────────────────────────────────────────────►

T0  本地已有 1..100
T1  发起 GET /messages?limit=50        服务端此刻最大 rowId = 100
T2  用户发送消息 → 写入 101
T3  响应到达，里面最大 rowId = 100
```

如果合并规则是"删掉所有 `orderKey > 远端最大"：

```text
本地 101 > 远端 100  →  判定为幽灵  →  删除
```

用户刚发的话没了。

### 4.2 根因

**"远端没有" ≠ "本地多余"。**

远端窗口是**有限的一页**（`limit=50`），它只覆盖某个区间。把"不在这一页里"当成"该删"，就把时间维度的误解当成了空间维度的判断。

### 4.3 解法：把删除范围收窄到一个可证明的区间

引入 `fenceMax` = **发起请求那一刻**的本地最大 `orderKey`。

```text
        已确认多余          在途写入            远端没覆盖
   ┌──────────────────┬────────────────┬────────────────────┐
   0              remoteMax         fenceMax            本地最大
        （远端窗口上界）      （发起请求时的本地最大）
```

只删除同时满足三条的行：

```text
1. orderKey > remoteMax     远端这一页里确实没有
2. orderKey <= fenceMax     它在发请求之前就已存在
3. 不在 pendingKeys         它不是本端刚提交待确认的
```

第二条是全部关键：它把"发请求之后才出现的行"从删除范围里**结构性地**排除了，而不是靠时序猜测。

### 4.4 代入 4.1 的场景

```text
remoteMax = 100, fenceMax = 100
删除区间 = (100, 100] = 空
→ 101 保留 ✅
```

### 4.5 围栏为什么必须是"发起前的基线"

如果传响应到达时的本地最大（102，因为期间又写了一条）：

```text
删除区间 = (100, 102]  →  101 和 102 都被删  ❌
```

所以 API 设计成两步：`openChannel` 返回 `fenceMax`，调用方**必须先拿到它再发请求**，最后把原值传回 `applyRemoteWindow`。

### 4.6 这套规则的边界

| 覆盖 | 不覆盖 |
|---|---|
| 单次窗口拉取期间的在途写入 | 多端并发写同一会话（无 CAS，后写覆盖） |
| 同通道内的顺序 | 跨通道的因果关系 |
| 已知的 pending 豁免 | 未知来源的第三方写入 |

## 五、核心原理：截断重绑定

### 5.1 问题

网关回滚截断后，**幸存行的 `rowId` 会变**。契约原文：

> After a truncation the survivor row ids let the client rebind its cached `rowId`s (`None` map entries: drop the cached id).

### 5.2 只删超界会怎样

```text
截断前：本地 rowId = [1, 2, 3, 4, 5]，目标 = 3
只删 > 3  →  剩 [1, 2, 3]
但网关把 1 重绑到 101、2 重绑到 102
下次回拉 →  本地 [1, 2, 3] + 远端 [101, 102]
           同一条消息存了两份  ❌
```

### 5.3 正确处理

```text
有 survivorMap  →  以它为唯一权威
                   值为数字 n  →  旧键 rebind 到 n
                   值为 null    →  删除
                   不在映射里且 > 目标  →  兜底删除
                   重绑定后同键冲突  →  按字段完整度择优，只留一份
无 survivorMap  →  退化为按 target 截断
```

### 5.4 三个阶段的铁律

```text
阶段 1  armed        用户点了回滚，请求还没返回
       → 只改内存 + 存内存快照，磁盘完全不动

阶段 2  成功          拿到 survivor_row_id_map
       → 删盘 + 重绑定 + 记墓碑

阶段 3  失败 / 取消    请求报错或用户取消
       → 恢复内存快照，磁盘从未被触碰

阶段 4  超时          结果未知
       → 内存标 stale + 立即回拉，磁盘不恢复也不删
```

**为什么阶段 1 不许碰磁盘**：用户点取消后，如果磁盘已经删了，历史就永久丢了 —— 而内存里还有快照可以恢复。

## 六、完整流程图

### 6.1 冷启动：缓存 → 首屏 → 后台对齐

```text
                     应用启动
                        │
           ┌────────────▼────────────┐
           │ restoreCacheToState()   │  ← 不依赖网络
           │ 读 sessions / agents    │
           └────────────┬────────────┘
                        │
        ┌───────────────┼───────────────┐
        │ state 为空?    │ 否             │ 是
        ▼               ▼               ▼
    跳过（已有数据）   跳过（网络先到）   填充 state
        │               │               │
        └───────────────┴───────┬───────┘
                                ▼
                          RENDER()  ← 列表立即可见
                                │
                    ┌───────────▼───────────┐
                    │ connect()  WebSocket   │  ← 与渲染并行
                    └───────────┬───────────┘
                                ▼
              ┌─────────────────┴─────────────────┐
              │ 权威拉取（profiles / sessions /    │
              │            groups）                │
              └─────────────────┬─────────────────┘
                                ▼
                    全量成功?  ──┴──
                    │             │
                   是             否
                    │             │
                    ▼             ▼
          覆盖 state + 写缓存   只合并，不删除，不写缓存
                    │             │
                    └──────┬──────┘
                           ▼
                     有差异才重渲染
```

**关键分界**：填充和渲染都在网络之前完成。绝不"等对齐完再渲染"——那就退化成每次启动都等网络。

### 6.2 打开会话：内存 → 磁盘 → 远端

```text
                    selectSession(id)
                           │
                           ▼
               ┌───────────────────────┐
               │ 内存 sessionMessagesCache 命中? │
               └───────────┬───────────┘
                    命中   │   未命中
              ┌────────────┴────────────┐
              ▼                         ▼
      直接渲染（0ms）           cacheService.openChannel()
              │                         │
              │                  返回 rows + fenceMax ★
              │                         │
              │              当前视口为空 ─┴─ 非空
              │                    │         │
              │                    ▼         ▼
              │              渲染磁盘行    跳过（不覆盖用户内容）
              │                         │
              └────────────┬────────────┘
                           ▼
              activeStreaming? ──是──► 到此为止（不覆盖流式状态）
                           │否
                           ▼
       ┌───────────────────────────────────────┐
       │ REST GET /messages?limit=50           │
       │ （即使缓存命中也要拉，缓存不负责"最新"）  │
       └───────────────┬───────────────────────┘
                       ▼
              竞态守卫：切走了? ──是──► 丢弃本轮结果
                       │否
                       ▼
        planSessionLoadMerge(远端, 本地, serverPriority)
                       │
                       ▼
       cacheService.applyRemoteWindow(ref, rows, fenceMax ★)
                       │           ↑ 传回基线，围栏生效
                       ▼
                 写 IndexedDB
                       │
                       ▼
              session.resume({ omit_messages: true })
                       │  ← 只兑换 live id 与运行态
                       ▼
                校正 running / inflight
```

★ 是整个流程里唯一的时序依赖：`fenceMax` 必须在 REST 请求**之前**取得。

### 6.3 `applyRemoteWindow` 内部

```text
         applyRemoteWindow(ref, remote, fenceMax, pending)
                          │
                          ▼
              ┌───────────────────────┐
              │ 通道锁：同通道串行      │
              └───────────┬───────────┘
                          ▼
              listMessages(本地最新 messageCap 条)
                          │
                          ▼
        ┌─────────────────────────────────────┐
        │ mergeRemoteWindow（纯函数）           │
        │                                     │
        │ 1. upsert：local ∪ remote           │
        │    同主键 ─► 字段完整度择优          │
        │                                     │
        │ 2. 逐行判定删除：                    │
        │    orderKey > remoteMax    ?        │
        │    orderKey <= fenceMax    ?        │
        │    不在 pendingKeys        ?        │
        │    三者全真 ─► 剔除                  │
        └────────────────┬────────────────────┘
                         ▼
              evictToCap(结果, messageCap)
                         │
                         ▼
              deleteMessages(该通道全部)
                         │
                         ▼
              putMessages(保留的行)   ← 整体替换，不残留幽灵
                         │
                         ▼
              返回 { rows（倒序）, evictedKeys, remoteMax }
```

**为什么先清后写**：围栏判定为幽灵的旧行如果只"不写入"，它们还留在库里。整通道替换保证磁盘状态与内存判定完全一致。

### 6.4 实时写入

```text
  网关推送
     │
     ├─ message.delta × N   ──► 只更新内存流式草稿，不写盘
     │                          （逐字落盘是纯 I/O 浪费）
     │
     ├─ tool.start / complete ──► 聚合进当前 assistant 行
     │
     └─ message.complete
             │
        persisted_turn.complete === true?
             │
      ┌──────┴──────┐
     是             否
      │             │
      ▼             ▼
 appendRows()   不写盘（契约：行号未被证明）
      │             │
      ▼             ▼
 写库 + 淘汰     触发一次 REST 回拉
      │
      ▼
 每会话超 500 行 → 按 orderKey 删最旧
```

### 6.5 群聊：独立的权威门

```text
            fetchGroupRooms()
                   │
                   ▼
        groups.list(client)
                   │
        ┌──────────┴──────────┐
       成功                   失败
        │                     │
        ▼                     ▼
 groupsAuthoritative=true   保留既有列表（不清空）
        │                     │
        ▼                     ▼
 覆盖 state + 写缓存        render()，不写缓存
        │
        ▼
 groups.log({ since_seq: latestSeq })
  后循环至 has_more === false
```

**为什么单独做权威门**：原来失败分支写的是 `state.groupRooms = []`，一次弱网抖动就把整列群聊清空。这违反"失败不可致空"。

### 6.6 删除传播

```text
  用户删除会话
        │
        ▼
  RPC 成功? ──否──► 恢复、提示失败，磁盘不动
        │是
        ▼
  dropChannel(ref)          ← 删该通道全部消息
        │
        ▼
  索引去掉该行 + 写回
        │
        ▼
  内存墓碑（内存即可：在途响应绑定当前连接，
           进程重启后连接已断，在途响应不存在）
```

## 七、一致性规则总表

| # | 规则 | 违反后果 | 守卫 |
|---|---|---|---|
| 1 | 权威门：只有全量成功才允许删除本地 | 一次弱网清空列表 | `authoritative` / `groupsAuthoritative` |
| 2 | 删除双向传播 | 幽灵复活 | `dropChannel` + 索引同步 |
| 3 | 同主键幂等 upsert，字段完整者胜 | 带工具调用的版本被空壳覆盖 | 定理 25 |
| 4 | 每通道上限按 `orderKey` 淘汰 | 同秒多行时删错 | 定理 23 |
| 5 | 不缓存运行态 | 重启后显示"仍在运行"，输入锁死 | 类型里根本没有 `running` 字段 |
| 6 | 截断以 `survivor_row_id_map` 为唯一权威 | 同一消息存两份 | 定理 24 |
| 7 | 围栏剔除（三条同时成立） | 在途写入被删 | 定理 22 |
| 8 | pending 不可删 | 未确认消息被并发回拉当幽灵 | 定理 26 |
| 9 | `profilesLoaded` 显式标记 | 持久化后永不刷新 | —— |
| 10 | 用户行不截断 | 回滚把半截正文当新提问提交 | —— |

## 八、验证：怎么证明它是对的

### 8.1 三层验证，各管一段

```text
┌────────────────────────────────────────────────────────────┐
│  形式化（fast-check）                                       │
│  5 条定理 × 150~200 runs                                   │
│  证：随机交错下不变量恒成立                                  │
│  跑：node --test .../cache-fence-formal.test.mjs           │
├────────────────────────────────────────────────────────────┤
│  单元（62 条）                                              │
│  证：每个等价类与退化边界的行为                              │
│  跑：node --test .../cache/*.test.mjs                      │
├────────────────────────────────────────────────────────────┤
│  E2E（11 条，真实 Blink + 真实 IndexedDB）                   │
│  证：接线正确 + 浏览器引擎认这个区间                          │
│  跑：node --test .../cdp/cache-cold-start-cdp.test.mjs     │
└────────────────────────────────────────────────────────────┘
```

### 8.2 为什么必须三层都有

| 只做 | 会漏掉 |
|---|---|
| 单元 | 随机交错下的反例（人工想不全三个布尔的组合） |
| 形式化 | 组件写对了但**没接线**（E2E 首次运行就抓到：缓存写完了，renderer 从没读过它） |
| E2E | 跑得慢，覆盖不了边界穷举 |

### 8.3 变异验证：证明测试能失败

| 变异 | 结果 | 说明 |
|---|---|---|
| `isWithinFence` → `true` | 仅定理 22 红，其余 4 条绿 | 断言精准打在围栏上，不靠连带失败 |
| `boundary - 1` → `boundary` | bounds 用例红 2 条 | 边界断言确实卡在减一这个动作上 |

## 九、边界与已知限制

| 限制 | 后果 | 现状 |
|---|---|---|
| 无多端冲突合并 | 两端同时改同一会话，后写覆盖 | 网关单权威，可接受 |
| 只缓存尾部 500 行 | 更早的按需分页拉 | 设计如此 |
| 群聊无下行事件 | 只能轮询 `groups.log(since_seq)` | 协议层限制 |
| Agent 无下行事件 | 只能启动 / 重连 / 聚焦时拉 | 协议层限制 |
| 离线时不弹连接层 | 有缓存也看不到内容 | **未解决**，属另一个特性 |
| 消息删除仅覆盖手工删除 | 截断删除路径尚未接线 | **待补** |
