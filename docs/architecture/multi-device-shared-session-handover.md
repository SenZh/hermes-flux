# Hermes Flux 多端无缝漫游与输入冲突终极解决方案
# (Multi-Device Shared Session Seamless Handover Spec)

> **问题定义**：当用户在多个设备（如工位 Mac/PC 桌面端、手机 iOS/Android、甚至网页端）同时打开同一个 Hermes Session 时，原生网关底层将运行中的会话标记为 `running: true`，此时另一端若尝试输入，经常遭遇“会话繁忙被拒（Session Busy / 4009）”、“输入被强行打断（Hard Interrupt）”或“两端打字冲突割裂”，无法做到类似协同文档或即时通讯般的顺畅多端漫游。

---

## 一、底层根因深度剖析 (Gateway Internal Architecture)

深入阅读 Hermes Gateway 源码（`tui_gateway/methods_prompt.py`、`prompt_turn.py`、`session_auto_continue.py`），发现导致该问题的核心机制：

1. **单会话单工运行锁（Session Running Lock）**：
   - 网关对每个 Session 维护一个 `session["running"]` 状态与 `history_lock`。当一端提交 Prompt 后，网关启动大模型生成与工具执行循环（Turn Loop），`running` 保持为 `true`。
2. **连接绑定覆盖（Transport Rebinding）**：
   - 当设备 B 发送 `prompt.submit` 时，网关执行 `_rebind_live_transport(sid, session, t)`，将该 Session 的“下行推送主通道”瞬间夺取转移到设备 B，导致设备 A 出现流式断流或白屏。
3. **繁忙模式处理策略（`_handle_busy_submit`）**：
   - 默认配置为 `interrupt`（打断优先）：设备 B 说话会直接给正在推理的 Agent 发信号强杀当前生成；若配置为 `queue` 则静默排队，用户无法感知；若配为严格模式则直接报 4009 `session busy` 拒绝输入。

## 二、Aura 多端共享会话解决方案：三大核心机制

为了让用户在电脑写一半，拿起手机就能接着说、接着看，Aura 在客户端架构层实现 **“设备主动让渡 + 语义级意图路由 + 多设备广播感知”** 的完整闭环：

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        Hermes Gateway (服务端)                         │
│   • 真实状态源 (State.db)   • Session Turn Lease (租约仲裁)           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ WebSocket 双向总线 (广播所有 events)
         ┌──────────────────────────┴──────────────────────────┐
         ▼                                                     ▼
┌─────────────────────────────────┐   ┌─────────────────────────────────┐
│     设备 A: Desktop (工位电脑)   │   │     设备 B: Mobile (手机 iPhone)│
│ • 状态: [观察者 Observer]       │   │ • 状态: [活跃发言者 Presenter] │
│ • 获得焦点/打字: 申请 Lease ────┼───┼─► 自动释放 Lease，界面平滑降级  │
│ • 实时同步对方的草稿输入态 (Presence)◄─┼───┼── 手机端正在输入指示符显示      │
└─────────────────────────────────┘   └─────────────────────────────────┘
```

### 1. 机制一：会话租约与主动让渡（Session Lease & Presence Handoff）

不再让两端在提交时发生硬碰撞，而是在**“开始打字”的瞬间就在端侧完成平滑协调**：

* **打字感知与租约握手（Typing Lease）**：
  - 当设备 A（手机）聚焦输入框并开始打字时，通过 WebSocket 向网关广播一个轻量级的 `presence.typing` 信号（携带 `device_id`, `device_name`）。
  - 设备 B（电脑）收到信号，输入框上方即时浮现气泡提示：*“📱 iPhone 正在输入...”*，电脑端的发送按钮自动转换为“队列发送”或“接管输入”，避免双手在两个设备同时敲回车产生竞态。
* **主动无缝接管（Takeover Handoff）**：
  - 如果用户在电脑上点“接管输入”，电脑端发送 `session.lease.claim`，手机端自动释放焦点并将未发送的文字暂存为本地草稿，平滑过渡。

---

### 2. 机制二：智能意图分流路由器（Smart Intent Router）

当 Agent 正在执行耗时任务（如跑 5 分钟测试、爬 50 篇论文），用户在另一端（手机）说话时，客户端**绝不盲目发 `prompt.submit` 导致被拒或强杀**，而是通过语义意图分流器判定执行通道：

| 用户输入意图 | 判定条件 | Aura 调用的底层协议 | 呈现效果与体验 |
|---|---|---|---|
| **1. 纠错/航向微调 (Steer)** | 用户输入以“改一下”、“换成”、“不对”、“优先”开头，或点击了“修正”按钮 | 调用 **`session.steer`** | **不打断模型当前执行步**，当前原子操作完成后，以最高优先级把修正注入下一步推理链。电脑手机两端同时浮现“已注入航向修正”。 |
| **2. 顺便补充 (By-The-Way)** | 用户补充背景信息、上传参考图，但不急于打断主流程 | 调用 **`prompt.btw`** | **静默追加**到当前正在执行的上下文末尾，Agent 在下一轮思考时自动纳入该信息，两端无感。 |
| **3. 排队追问 (Queue Follow-up)** | 完整的新任务（如“跑完这个后，再把那个接口测一下”） | 携带 `queued: true` 的 **`prompt.submit`** | 网关将其压入 `queued_prompts` 队列。输入框下方出现排队任务卡片，当前任务一跑完，自动流水线触发，电脑手机两端状态完全对齐。 |
| **4. 强行终止并重开 (Hard Override)**| 用户明确要求“停下”、“重写”或点击强行发送 | 先调 `session.interrupt`，紧随 `prompt.submit` | 优雅停止当前推理，将控制权交给当前操作的设备。 |

---

### 3. 机制三：多端广播分发器（Multi-Transport Fan-out Relay）

原网关的痛点是设备 B 一发言，设备 A 就断流。Aura 在客户端网络层设计了**端侧多路复用协同协议**：

1. **下行广播订阅（Subscription Preservation）**：
   - 客户端连接网关时，声明 `viewer_mode: true` 与 `shared_session_id`。网关在 `_rebind_live_transport` 中将该 Session 的下行事件向所有已连接的 Viewer 广播，而不是粗暴地只发给最后一个人。
2. **多设备流式镜像（Mirror Streaming）**：
   - 电脑上点击了回车，手机端的屏幕也**以完全一致的 120 FPS 打字机速度实时吐字**；
   - 手机端点了审批（Approval 弹窗确认），电脑端的审批模态卡片瞬间同步消失并变为“已在手机上批准”。

## 三、用户真实使用场景与体验效果

* **场景：工位 ➔ 咖啡厅无缝接力**
  1. 用户在工位 Mac 上输入：“帮我把项目重构并跑完全量单测”，Agent 开始敲代码跑测试；
  2. 用户合上电脑，掏出手机下楼买咖啡，手机 App 打开时**秒开会话**，屏幕上实时显示 Mac 上遗留的测试流进度；
  3. 此时 Agent 弹出高危命令审批（`approval: rm -rf dist`），手机弹出触觉震动与弹窗，用户在手机上点击“批准”；
  4. 随后用户在手机输入：“顺便把更新日志也写了”，Aura 自动识别为 `queued: true` 优雅排队；
  5. 买完咖啡回到工位打开 Mac，电脑屏幕已无缝显示在手机上追加的任务与最终交付结果，**没有任何一次报错，没有任何一次冲突**。
