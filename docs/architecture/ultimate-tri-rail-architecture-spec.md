# Hermes Flux 桌面端终极多智能体协同架构规范 (v4.5)
## —— 实体定义、双轨导航、多模态工具舱与端到端工程落地方案

## 零、 方案背景与问题陈述 (Context & Problem Statement)

在构建面向 Hermes Agent 生态的旗舰级工作台 **Hermes Flux** 时，传统 AI 客户端（或单一 ReAct Harness 包装器）在面对复杂现实工程时存在四大不可调和的结构性痛点：
1. **概念混淆与拓扑死锁**：机械套用“左上角切 Agent ➔ 过滤出会话列表”的单树层级，导致跨角色的**群组（Group）**无处安放、随用随弃的**临时旁聊（Side Session）**四处漂移；
2. **上下文污染与破坏**：在同一个长会话里随意换人或强行切工作目录，导致 Agent 的提示词（System Prompt）串味、代码路径错乱、长期记忆被杂乱历史严重稀释；
3. **沟通场与交付场脱节**：聊天框里讨论了上百轮方案，但方案无法收敛为确定性的工单；多 Agent 并行干活缺乏沙箱隔离，极易引发 Git 分支冲突与盲目等待焦虑；
4. **底层协议与前端空想脱节**：脱离了 Hermes 官方真实的网关状态机（如 `profiles.*`、`hosted_rooms`、`canonical_session`、`projects_db`）进行不可落地的 UI 空想。

本规范彻底终结上述混乱，从底层网关协议出发，确立清晰的**四大核心实体定义**，并落地**“左侧核心业务主线 + 中间 720px 流式主对话 + 右侧多模态工具舱”**的终极极客美学交互架构。

## 一、 核心概念与底层物理事实明确 (First Principles & Definitions)

在 Hermes Flux 的体系中，所有实体拥有明确的层级、物理归属与协议映射，严禁概念混淆：

### 1.1 物理文件夹 (Folder) vs 工作区 (Workspace) vs 项目 (Project)

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 层级 3: Project (项目) ── 【业务与协作视角】                           │
│         人为定义的工程联合体，聚合 1 个主目录与多个关联目录，绑定看板  │
├────────────────────────────────────────────────────────────────────────┤
│ 层级 2: Workspace (工作区) ── 【Git 与执行视角】                       │
│         底层防穿帮的物理隔离单元 (官方源码: workspace_key = git_root || cwd) │
├────────────────────────────────────────────────────────────────────────┤
│ 层级 1: Folder (文件夹) ── 【操作系统文件系统视角】                     │
│         磁盘物理路径，如 /opt/data/projects/hermes-flux                │
└────────────────────────────────────────────────────────────────────────┘
```

* **物理文件夹 (Folder)**：磁盘物理路径，不带任何 AI 状态机属性；
* **工作区 (Workspace)**：Hermes 官方状态机中防会话穿帮的自洽代码单元。底层源码定义：`workspace_key = row.git_repo_root or row.cwd`。一个 Git 仓库就是一个天然的工作区。会话一生锚定并冻结（Frozen CWD）在其创建时的目录中；
* **项目 (Project)**：基于 `hermes project`（官方 `projects_db.py`）的高维业务工程实体：
  - 拥有一个 **Primary Folder（主目录，作为默认 CWD）** 与若干关联文件夹；
  - 拥有唯一的 `project_id`、`slug` 与元数据；
  - **绑定专属看板（`bind-board`）**：为后台执行 Worker 提供确定性的 Git Worktree 与分支生成规则。

### 1.2 个人主助理 (Default Soul) vs 专职数字员工 (Bot) vs 临时旁聊 (Side Session)

* **个人主助理 (Default Soul / HQ)**：
  - 物理路径：`~/.hermes/`（Default Profile）；
  - 业务定位：用户的“首席数字幕僚长兼总中枢管家”，拥有全局最高的置顶权重与跨领域调度能力；
* **专职数字员工 (Bot / Resident Agent)**：
  - 物理路径：`~/.hermes/profiles/<name>/`（如 `arch-wang`、`fe-zhang`）；
  - **独立沙箱**：拥有独立的 `SOUL.md`、`profile.yaml`、独立的技能与 MCP 工具集、独立的 `state.db` 数据库；
  - **唯一主工位（Canonical Forever-Chat）**：在底层数据库中标题固定为 `'Bot Chat'` 且 `hidden=1`。这是专家的终身会话，带有 `Teammate Protocol`（具备花名册感知与 `message_agent` 能力），支持 `Capability Epoch` 指纹热重构，永不自动冷归档；
* **临时旁聊 (Side Session / Scratchpad)**：
  - 物理属性：`hidden=0, archived=0`，随机生成 UUID 的普通会话；
  - 业务定位：随用随扔的特定攻坚、命令报错排查、单点推演；
  - **单 Agent 强绑定**：每个旁聊一生只能独占归属于一个指定的 Agent（Profile），选定后不可篡改，物理隔离上下文。

### 1.3 协同群聊会议室 (Group / Hosted Room)

* **物理定位**：由网关服务（Hosted Room Service）统一调度，存储在网关主数据库的 `hosted_rooms` 表中，**独立于任何单个 Profile**；
* **业务定位**：多 Agent（2 到 6 人）共同参会的议事房间，支持 `@<handle>` 精准唤醒与全员广播；
* **上下文隔离**：群聊记录保存在房间事件流（`groups.log`）中，**绝不回写污染单个 Bot 的个人私聊记忆（`MEMORY.md`）**。

### 2.1 左侧双轨中枢 (LeftRail: 48px Station Rail + 212px Context Drawer = 260px)

彻底摒弃死板的左上角单点下拉与 4 层手风琴堆叠，以 **Station（实体）+ Drawer（投影）** 双轨化解信息爆炸：

1. **48px Station Rail（物理中枢微轨）**：
   - **恒定置顶位**：`✦ 个人主助理 (Default Soul)`，带翡翠微光呼吸点，永远是用户的全局总台；
   - **专职数字员工位**：垂直排布具名 Bot 头像徽章（32×32px 超椭圆），具备专属色彩指纹（架构师靛青 `#4F46E5`、前端洋红 `#DB2777`、审查员琥珀 `#D97706`），带有后台运行状态指示点；
   - **协同会议室位**：`👥 群组`（展示叠落头像）；
   - **底部控制位**：`+`（新建 Bot 或加入群聊）与 `⚙`（设置）。
2. **212px Context Drawer（动态上下文抽屉）的严格联动规则**：
   - **当在微轨选中 Bot A 时**：
     * **上半区【专属旁聊】**：**严格仅展示 Bot A 名下的旁聊**（从 Bot A 专属的 `state.db` 读取，单 Agent 独占不可变，走默认 Workspace）；
     * **下半区【归属项目】**：展示全局工程项目树，但**自动置顶高亮 Bot A 参与的项目会话**，点击新建默认派发给 Bot A；
   - **当在微轨选中主助理 (Default) 时**：
     * 上半区展示全局中枢会话流，下半区展示所有项目会话的全景树（上帝视角）；
   - **当在微轨选中群聊时**：
     * 抽屉上半区自动折叠，直观列出当前所有多 Agent 研讨房间（基于 `groups.list`）。

#### 2.1.1 关键交互闭环：进入旁聊后如何随时回到 Bot 的主工位？（三重回程通道）
当用户进入了某个专职 Bot（如 Bot A 老王）的派生旁聊后，为彻底杜绝“迷失在临时旁聊、找不到主会话”的致命交互痛点，系统确立**“三重回程通道 (Triple Home Channels)”**：
1. **通道一（抽屉置顶锚点）**：抽屉上半区的第一行**永远恒定置顶展示该 Bot 的主工位**：`👑 核心主工位 (Forever-Chat) [置顶 · 终身主线]`，点击立即回归主干；
2. **通道二（微轨再次点击）**：对标 macOS Dock 与 Slack 交互本能，**在微轨上再次点击当前处于激活态的 Bot 头像（Click-Again）**，触发工作台“立即回到该 Bot 主工位”的快捷回程；
3. **通道三（中舱面包屑回退）**：中间主舱顶栏完整呈现血缘链路：`顶栏: 🤖 架构老王 ➔ ⑂ [旁聊] 锁冲突排查  [⮌ 回到主工位]`，点击左侧父级面包屑或回退胶囊即可瞬切归位。

3. **三态极客折叠**：
   - `Default (260px)`：双轨全开；
   - `Compact (48px)`：按快捷键 `Cmd+\`，收起 212px 抽屉，仅留微轨，悬停图标弹出 Floating Flyout；
   - `Zen (0px)`：按快捷键 `Cmd+B`，侧栏全隐藏，专注全屏协作。

### 2.2 中间主工作舱 (MiddlePod) 与 740px 悬浮输入舱

1. **黄金通栏流式阅读**：
   - 消息流容器水平撑满，内部约束在 **720px 黄金阅读宽度** 居中呈现，消灭宽屏下的空洞留白与眼疲劳；
2. **派生任务执行进度卡片（Worker Delegation Card）**：
   - 当 Bot 在项目目录派生后台任务执行代码时，主对话流内不刷新全屏，而是内嵌一张紧凑的极客风进度卡片；
   - 卡片显示 PID、目标目录、当前执行命令，并自带两大直达操作：`[ ⚡ 穿透查看实时终端 ➔ ]` 与 `[ 🔍 审查代码变更 ]`；
3. **740px 黄金悬浮输入舱 (InputDock)**：
   - 底部悬浮毛玻璃容器（`backdrop-filter: blur(20px)`），锁定 `max-width: 740px`；
   - 支持 IME 输入法组合态保护（输入中文按 Enter 绝不误发送）；
   - 支持键盘流快速触发：键入 `@` 呼叫专家，键入 `/task` 派发工单，键入 `/btw` 临时外援问答。

### 2.3 右侧多模态工具舱 (RightPod / InspectionPod: 380px)

定位为**“确定性状态收敛与工程交付”**，通过顶部分段 Tab 承载三大模态并实现丝滑互通：

1. **平时态 ➔ [📋 看板 (Kanban)]**：
   - 自动绑定当前项目的迭代看板（Backlog ➔ Todo ➔ Doing ➔ Done）；
   - 在中舱讨论完敲一句 `/task`，卡片实时在右侧浮现并推进；
2. **干活态 ➔ [⚡ 穿透终端 (Terminal)]**：
   - 点击中舱卡片上的 `[⚡ 穿透终端]`，右侧瞬间切至该 Worker 的虚拟控制台，120FPS 实时滚动打印测试与编译日志；
3. **审查态 ➔ [🔍 代码审查与门禁 (Diff & Gates)]**：
   - Worker 跑完后自动切入 Diff 审查；
   - 上半部展示类似 VS Code 的高亮对比代码块（+42, -6），下半部展示 **6 大工业级硬门禁状态卡片（Gate 0~5）**，点击底部绿色按钮即可一键合并归档！
4. **性能保活不变量**：
   - 采用 **“Headless 环形缓冲 + CSS `contain: strict; visibility: hidden;` + 渲染挂起”**；
   - 工具舱折叠收起时，后台日志正常吞吐，重新展开零延迟恢复，中舱打字输出毫无卡顿。

## 三、 端到端用户交互旅程与状态机 (End-to-End User Journeys)

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        四大标准用户使用旅程                            │
├────────────────────────────────────────────────────────────────────────┤
│ 旅程 1: 新建/选择项目 ➔ 物理工作区自动锚定至工程目录 (CWD 冻结)        │
│ 旅程 2: 主对话方案共商 ➔ 键入 @ 轻量外援，或一键四阶管道原地拉群      │
│ 旅程 3: 方案敲定推工单 ➔ /task 写入看板，Bot 派生 Worktree 沙箱开跑    │
│ 旅程 4: 中舱卡片一键穿透 ➔ 右侧看终端流水，测试跑通切 Diff 终审合并   │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.1 单聊一键拉群 (Session-to-Group Promotion) 四阶工程管道
在 MiddlePod 顶栏点击 `👥 原地拉群` 或键入 `@all`，触发以下四阶原子操作：
1. **阶段 1 (选人与确认)**：弹出微距选择器，勾选参会专家（如主助理 + 架构老王 + 前端小张）；
2. **阶段 2 (简报提取)**：客户端调用网关内置轻量归纳模型，提取当前会话前序共识，生成一份 Markdown 格式的《会议前序背景简报》；
3. **阶段 3 (创建房间与种子注入)**：
   - 调用官方 RPC `groups.create({ name: groupName, members: selectedProfiles })` 获得 `room_id`；
   - 调用官方 RPC `groups.send({ room_id, text: briefingMemo, is_seed: true })` 固化为 Room 0 号种子备忘录；
   - 原单聊末尾留下只读卡片：`已升级为多智能体群聊 [进入会议室 ➔]`；
4. **阶段 4 (视口无缝平移)**：左侧微轨切至 `👥 群聊`，中舱瞬切为多 Agent 群聊流，参会 Bot 带着完整前序背景直接开聊。

### 3.2 模式 B 全权交接 (Handoff & Fork) 落盘规则
在主对话中指定老王接管任务时：
- **物理落盘**：底层自动调用 `session.branch_whole`，在老王名下派生一个**独立的专项旁聊 Session**（绑定老王 Profile，继承历史）；
- **主记忆保护**：老王自己的终身主工位（Canonical Chat）完好无损，绝不灌入杂乱上下文；
- **任务归档**：老王在该专项旁聊里改完代码后，会话可随时归档，经验单向沉淀进其记忆库。

## 五、 质量门禁与实施准则 (Verification & Quality Gates)

所有后续落地编码必须无条件通过 `AGENTS.md` 规定的 **6 大质量门禁**：
1. **Gate 0: 架构符合性** —— 表现层禁止绕过 Core 直接执行系统命令或私自拼凑临时网络结构；
